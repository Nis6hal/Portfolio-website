The Problem & Context

Many university departments manage physical library assets through fragmented spreadsheets or manual paper ledgers. This results in lost inventory, untracked book renewals, and manual calculation of late fines.

UniLib was built to provide an institutional-grade platform: centralizing thousands of titles, automating member check-out/return cycles with barcode scanning readiness, and giving department heads live metrics on book circulation.

System Features

Catalog & Inventory Management

ISBN-based lookups, volume copy tracking, shelf aisle tagging, and automated out-of-stock reservation queues.

Automated Borrow / Return Flow

Streamlined checkout modal calculating automatic due dates, email reminder triggers, and automated overdue penalty calculations.

Overdue & Fine Management

Automatic overdue detection with configurable daily fine calculations, auto-generated fine records, and one-click payment settlement.

Circulation Analytics

Visual reports on most-borrowed topics, active reading trends, student delinquency rates, and inventory audits.

Engineering Challenges & Solutions

Challenge 1: Race Conditions in Last-Copy Book Reservation

When multiple students attempt to reserve the final copy of a popular textbook simultaneously, race conditions can cause negative stock counts. Implemented SQLite atomic transactions with check-then-decrement guard clauses to guarantee ACID compliance.

Challenge 2: Efficient Multi-Field Catalog Indexing

Searching across tens of thousands of books by title, author, ISBN, and tags caused slow table scans. Created SQLite B-tree and full-text search indexes with weighted scoring, reducing query response times from 340ms to under 18ms.

Database Schema & Core Tables

UniLib's data layer is modeled around a normalized relational schema designed for transactional integrity and fast lookup performance. The core entities are members, books, and circulation events.

Members Table

Stores member profiles, card IDs, contact details, membership status, and fine balances. Unique member card numbers are indexed for O(1) lookup at checkout terminals.

Books & Copies

Two-tier model: a books record for the title/ISBN metadata and a book_copies table tracking individual physical volumes, shelf location, and per-copy status.

Circulation Ledger

Every borrow and return is recorded as an immutable ledger row with timestamps, due dates, and staff IDs. This powers all overdue calculations and audit reporting.

Fines & Payments

Automated fine accrual records tied to circulation IDs, with payment settlement transactions that update member balances atomically.

Backend API Design

The Flask REST API follows a resource-oriented design with consistent HTTP semantics. All mutating endpoints use SQLite transactions wrapped in try/except blocks to roll back on any failure.

RESTful Resource Mapping

Endpoints map cleanly to resources: GET /books, POST /members/:id/borrow, POST /returns, and GET /analytics/circulation.

Input Validation & Sanitization

Every request payload is validated against schema constraints before hitting the database, preventing SQL injection and malformed data from corrupting the circulation ledger.

Analytics Endpoints

Aggregation queries pre-compute daily circulation summaries, most-borrowed title rankings, and member delinquency rates for the admin dashboard.

Technical Deep-Dive: Atomic Borrow Transaction

The borrow operation is the most critical path in the entire system. It must decrement available copies, create a circulation record, and set the due date — all as a single atomic unit. Here is the core logic:

SQLite Transaction Guard

# Check-then-decrement inside a single transaction
cursor.execute("BEGIN IMMEDIATE")
try:
    cursor.execute(
        "SELECT available FROM book_copies WHERE book_id = ? AND status = 'available' LIMIT 1",
        (book_id,)
    )
    row = cursor.fetchone()
    if not row:
        raise Exception("No copies available")

    cursor.execute(
        "UPDATE book_copies SET status = 'borrowed', member_id = ? WHERE book_id = ? AND status = 'available'",
        (member_id, book_id)
    )

    cursor.execute(
        "INSERT INTO circulation (member_id, book_id, due_date) VALUES (?, ?, datetime('now', '+14 days'))",
        (member_id, book_id)
    )
    conn.commit()
except Exception:
    conn.rollback()
    raise

Using BEGIN IMMEDIATE acquires a write lock before any reads, preventing the classic "last copy reservation race" where two concurrent requests both see an available copy and both proceed to borrow it.

Design Decisions & Trade-offs

SQLite over PostgreSQL

Why: Zero external infrastructure — the app runs on a single binary with no server setup. Trade-off: Concurrent write throughput is limited to single-writer, which is fine for library circulation but would bottleneck at massive scale.

Two-Tier Book Model

Why: Separating title metadata from physical copies means updating an author name or ISBN affects one row, not hundreds of copy records. Trade-off: More joins in queries, mitigated by indexing.

Client-Side React, Server-Side Flask

Why: Keeps the frontend lightweight and the backend simple. No SSR complexity. Trade-off: Initial page load ships a heavier JS bundle — acceptable for an internal admin tool.

What I'd Do Differently

If I were to rebuild UniLib today, I'd move the catalog search to a dedicated search engine like Meilisearch or Typesense instead of SQLite FTS. The weighted scoring I built manually works well, but a purpose-built engine would give typo tolerance and ranking out of the box. I'd also add a proper migration layer (Alembic) from day one — starting with raw SQL DDL made schema evolution painful as requirements shifted.

Lessons Learned & Outcomes

Building UniLib reinforced how critical atomic transactions are in inventory systems. Even a brief race condition can cascade into lost or duplicated book records. The indexing work also showed that query optimization is an ongoing process — as the catalog grows, new access patterns demand fresh indexes.

The system successfully automated the full circulation workflow for academic libraries, eliminating manual ledger errors and giving administrators real-time visibility into book demand and member activity.
