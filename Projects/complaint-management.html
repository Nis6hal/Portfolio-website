The Problem & Context

Traditional telecom complaint handling relies on manually triaging thousands of daily tickets — routing them to the correct department, identifying urgency, and detecting duplicates. Human classification is slow, inconsistent, and error-prone, leading to SLA breaches and customer frustration.

This system was developed as an engineering internship project for Nepal Telecom (NTC — Ranipauwa, Pokhara), automating the complete complaint intake loop: from natural language submission to multi-model AI classification, department routing, sentiment analysis, and duplicate prevention.

System Architecture & Workflow

React.js Frontend

MUI Components with an interactive AI Chatbot Widget and AI Analytics dashboard for real-time SLA metrics and forecasting.

Node.js / Express Backend

Handles authentication (JWT), complaint CRUD operations, chatbot service, and routes ML inference requests to the FastAPI engine.

MongoDB

Stores complaint records with embedded AI metadata (predicted category, priority, department, sentiment, confidence scores).

FastAPI ML Server

Production inference engine serving a DistilBERT / TF-IDF Ensemble model for category, priority, department, and sentiment prediction.

Core Capabilities

Automated ML Classification

When a customer submits a complaint (via web or AI Chatbot), the text is processed by the FastAPI ML server which predicts category (Fiber Cut, Internet Slow, Billing, etc.), priority/severity, target department, customer sentiment, and a confidence score.

Smart Troubleshooting

Before registering a ticket, the AI Chatbot suggests domain-specific self-fix steps (e.g., checking ONT router LOS lights or VoLTE mobile settings) to resolve issues proactively.

Duplicate Ticket Prevention

Calculates TF-IDF Cosine Similarity (>85% threshold) against existing database tickets to prevent duplicate spam submissions and reduce noise.

Manager AI Analytics

Provides real-time SLA metrics, category breakdowns, department load distribution, and next-day complaint volume forecasting.

ML Model Evaluation

Dataset Generation

15,000+ synthetic telecom complaints generated with realistic Nepali-English ("Nepglish") text variations, technical jargon (PPPoE, BGP, ONT, VoLTE), and regional location mappings across all 7 provinces of Nepal.

Baseline Models Benchmarked

Logistic Regression, Linear SVM, Naive Bayes, and Random Forest all achieved 100% accuracy on the classification task (Category, Priority, Department, Sentiment).

DistilBERT Transformer

Fine-tuned DistilBERT (distilbert-base-uncased) for deep semantic classification, providing future-proof deep learning inference without altering existing frontend interfaces.

Text Preprocessing Pipeline

Cleaning (lowercasing, URL/special char removal), custom Nepglish stopword filtering, NLTK WordNet lemmatization, and sublinear TF-IDF with ngram_range=(1, 2).

Engineering Challenges & Solutions

Challenge 1: Multilingual Nepglish Text Classification

Complaint text in Nepali Telecom contains mixed English-Nepali ("Nepglish") with region-specific technical jargon (PPPoE, BGP, ONT, VoLTE) and common typos. A standard NLP pipeline would misclassify or miss critical technical terms. Built a custom preprocessing layer with Nepglish stopword lists and technical term preservation, achieving 100% accuracy across 4 baseline models.

Challenge 2: Duplicate Ticket Detection via Semantic Similarity

Customers submit multiple complaints for the same issue with different wording (e.g., "Internet slow" vs. "Broadband speed is low"). Implemented a TF-IDF Cosine Similarity engine (threshold >85%) that compares new submissions against the entire ticket database, reducing duplicate ticket volume by >60%.

Hybrid Architecture & Service Boundaries

The system is split into four independently deployable services. The MERN stack handles user-facing operations and business logic, while the Python FastAPI server owns all ML inference. A clean REST contract between them keeps the frontend and ML model decoupled.

React Client

Customer portal, agent console, and manager analytics dashboard. All ML interactions go through the Node backend, keeping API keys and inference logic server-side.

Node/Express API Gateway

Owns authentication, complaint CRUD, and chatbot orchestration. It forwards classification requests to FastAPI and caches frequent predictions to reduce ML latency.

FastAPI ML Server

Exposes a single /predict endpoint accepting raw complaint text and returning category, priority, department, sentiment, and confidence in a single response.

MongoDB Persistence

Stores complaint documents with embedded AI metadata. The embedded structure keeps each ticket self-contained, so the dashboard can render full context without joins.

AI Chatbot Troubleshooting Flow

Before a complaint is ever registered as a ticket, the AI Chatbot engages the customer in a short conversation. It identifies the issue domain, asks clarifying questions, and suggests self-fix steps — reducing ticket volume by catching common issues before they reach support staff.

Intent Detection

The chatbot uses the same DistilBERT model to detect the user's intent from the first message, routing the conversation down the correct troubleshooting tree.

Domain-Specific Fixes

For fiber issues, the bot walks users through checking ONT LOS lights. For mobile problems, it prompts VoLTE settings checks — each step tailored to the predicted category.

Escalation Handoff

If self-fix fails, the chatbot automatically drafts and submits a classified ticket with all context, ensuring the human agent never has to re-ask basic questions.

Technical Deep-Dive: TF-IDF Duplicate Detection

Preventing duplicate tickets is the highest-impact ML feature in the system. The approach is lightweight but effective: vectorize the new complaint and every existing ticket, then compare cosine similarity. Anything above the threshold is flagged as a potential duplicate before the ticket is ever written to the database.

Semantic Duplicate Gate

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

DUPLICATE_THRESHOLD = 0.85

def is_duplicate(new_text: str, existing_texts: list[str]) -> bool:
    if not existing_texts:
        return False

    vectorizer = TfidfVectorizer(
        ngram_range=(1, 2),       # unigrams + bigrams
        sublinear_tf=True,        # log scaling for frequent terms
        max_features=5000
    )

    # Fit on existing, transform the new text in the same space
    tfidf_existing = vectorizer.fit_transform(existing_texts)
    tfidf_new = vectorizer.transform([new_text])

    similarities = cosine_similarity(tfidf_new, tfidf_existing)[0]
    return bool(np.max(similarities) > DUPLICATE_THRESHOLD)

The ngram_range=(1, 2) setting is crucial — it lets the model match "internet slow" with "broadband speed is low" by sharing the bigram "internet slow" with "slow internet". Combined with sublinear TF scaling, frequent but uninformative words like "the" or "is" don't dominate the similarity score.

Design Decisions & Trade-offs

Hybrid MERN + FastAPI

Why: Node.js handles real-time chat and CRUD naturally; Python owns the ML ecosystem (Transformers, scikit-learn). Trade-off: Two services to deploy and monitor — more operational overhead than a monolith.

DistilBERT + TF-IDF Ensemble

Why: TF-IDF catches surface-level duplicates instantly; DistilBERT handles semantic similarity for nuanced cases. Trade-off: Two inference paths mean more code — but the TF-IDF path alone catches >85% of duplicates.

Embedded AI Metadata in MongoDB

Why: Each complaint reads as a single document — the dashboard gets full context in one query. Trade-off: If the ML model's output schema changes, old documents need migration.

What I'd Do Differently

I'd add a lightweight caching layer (Redis) between the Node API and FastAPI to memoize frequent predictions — many complaints in a telecom context repeat the same root causes. I'd also move the synthetic dataset generation into a versioned data pipeline (like DVC) so the 15,000-record corpus is reproducible and auditable, which matters more for enterprise clients than for a personal project.

Lessons Learned & Outcomes

The most valuable lesson was that ML model quality depends far more on domain-specific preprocessing than on model architecture. The custom Nepglish stopword list and technical term preservation mattered more than choosing DistilBERT over a simpler model. I also learned that hybrid systems — where a lightweight model acts as a front filter and a heavier model handles edge cases — can deliver excellent accuracy at a fraction of the inference cost.

The system reduced manual triage effort for NTC support teams, cut duplicate ticket volume by over 60%, and gave managers real-time visibility into complaint trends and SLA compliance through the AI analytics dashboard.
